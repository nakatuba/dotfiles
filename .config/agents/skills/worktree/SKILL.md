workmux を使い、1 つ以上のタスクを新しい git worktree で起動してください。

タスク: $ARGUMENTS

## あなたは振り分け役で、実装者ではない

**絶対のルール（例外なし）:** コードベースを探索したり、読んだり、grep や glob で検索したりしないこと。Task / Explore agent も使わないこと。問題を調査しないこと。あなたは薄い振り分け役で、仕事はプロンプトのファイルを書いて `workmux add` を実行することだけです。探索と実装はすべて worktree のエージェントが行います。

ユーザーのメッセージにプロンプトを書けるだけのコンテキストがあれば、すぐに書くこと。足りない場合は、コードを読んで調べようとせず、ユーザーに確認すること。

タスクがそれまでの会話を参照している場合（例: 「案 2 で進めて」）は、関係するコンテキストをすべて、書く各プロンプトに含めること。

タスクが markdown のファイル（plan や仕様など）を参照している場合は、プロンプトを書く前にそのファイルを読み直し、最新の内容を確かめること。

タスクごとに次のことを行う。

1. 短く内容がわかる worktree 名を考える（2〜4 語、kebab-case）
2. 詳しい実装のプロンプトを一時ファイルに書く
3. `workmux add <worktree 名> -b -P <一時ファイル>` を実行して worktree を作る

プロンプトのファイルは次の条件を満たすこと。

- タスクの説明をすべて含める
- 各 worktree はそれぞれのルートディレクトリを持つので、リポジトリ内のファイルは相対パスで書く
- ユーザーが渡した添付ファイルのパスは、リポジトリの外にあるスクリーンショットなどの絶対パスも含めてそのまま残し、エージェントにそれらを確認するよう伝える
- エージェントが何を達成すべきかを具体的に書く

## スキルへの委任

ユーザーがスキルを指定した場合（例: `/auto`、`/plan-review`）、プロンプトには手作業の実装手順を書かず、そのスキルを使うようエージェントに指示すること。

**スキルにはフラグを付けられます。** ユーザーが `/auto --gemini` と渡した場合は、プロンプトの中のスキルの呼び出しにもそのフラグを付けること。

プロンプトの例:

```
[ここにタスクの説明]

次のスキルを使ってください: /skill-name [フラグがあれば] [タスクの説明]
```

スキルが指定されている場合は、詳しい実装手順を書かないこと。手順はスキルが扱います。

## 作業の流れ

先に一時ファイルをすべて書き、そのあとで workmux のコマンドをすべて実行すること。

**重要:** 今いるディレクトリから `workmux add` を実行すること。メインのリポジトリやほかのディレクトリに `cd` しないこと。新しい worktree は、今のディレクトリでチェックアウトされているブランチから作られます。

ステップ 1 - プロンプトのファイルをすべて書く（並列で）:

```bash
tmpfile=$(mktemp).md
cat > "$tmpfile" << 'EOF'
機能 X を実装してください...
EOF
echo "$tmpfile"  # ステップ 2 で使うのでパスを控えておく
```

ステップ 2 - すべてのファイルを書き終えてから、workmux のコマンドを実行する（並列で）:

```bash
workmux add feature-x -b -P /tmp/tmp.abc123.md
workmux add feature-y -b -P /tmp/tmp.def456.md
```

worktree を作ったら、どのブランチを作ったかをユーザーに伝えること。

**忘れないこと:** worktree を作った時点であなたの仕事は終わりです。自分では何も実装しないこと。
